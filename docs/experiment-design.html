The Radio Probe — experiment design

Reproduction of Openpi Comet: Competition Solution for the 2025 BEHAVIOR Challenge (arXiv:2512.10071v3). Empiricist role.

Machine: marklxxxv — RTX 3090 (Ampere, sm_86), 24 GB, 24 cores, 31 GB RAM Stack: BEHAVIOR-1K v3.7.2 · Isaac Sim 4.5 / Kit 106.5 · torch 2.6.0+cu124 · numpy 1.26.4 Policy: released pi05-b1kpt50-cs32 (openpi-comet)

1. Hypothesis

Everything is measured on a single task, turning_on_radio.

  • It is their probe task. Every cell of Table 3 and Table 4 was measured on it. Using the same task removes the "different task, different model" confound entirely.
  • They make an extreme claim about it. Fig 4 reports 1.00, and the caption says the policy performs it "robustly." That is falsifiable in a way that a directional claim is not.
  • It is the cheapest task in the benchmark. 934 frames = 31 s at 30 fps — 2.5× shorter than the next-shortest (hanging_pictures, 2341 frames). Cheapest possible test of the strongest possible claim.

The three sub-hypotheses, all drawn from Table 3:

Claim Paper's value
H1 Temporal Ensemble and Receding Temporal fail to produce stable closed-loop behaviour 0.00
H2 Native resolution more than doubles success vs 224×224 0.30 → 0.60
H3′ Control quality degrades with shorter executed action chunks — (variant, see §4)

All three are runtime flags (scripts/serve_b1k.py:67-72), so released checkpoints make them testable with no training.

2. Design

Six configs, one factor at a time around a baseline, mirroring Table 3's own block structure.

Config Control mode max_len Resolution Tests Paper
A_baseline_rh32_224 receding horizon 32 224 Fig 4 headline 1.00
B_temporal_ensemble temporal ensemble 32 224 H1 0.00
C_receding_temporal receding temporal 32 224 H1 0.00
D_native_resolution receding horizon 32 native H2 0.60
E_maxlen16 receding horizon 16 224 H3′ —
F_maxlen8 receding horizon 8 224 H3′ —

Ordered by information value, so the headline claim and the arm most likely to move land first if the run is cut short. Resolution is a single env-wrapper swap — RGBWrapper replaces 224×224 with the native HEAD_RESOLUTION/WRIST_RESOLUTION.

Sample size — we use twice the paper's

The public instance list holds 20 IDs for this task:

242, 295, 211, 203, 109, 181, 197, 187, 214, 139, 185, 102, 246, 105, 271, 119, 220, 224, 212, 298

but the harness defaults to m.NUM_EVAL_INSTANCES = 10. That is why every number in Fig 4 and Table 3 lands on a multiple of 0.1. Because the task is only 31 s, we raise the cap to 20 and run all of them — then report the first-10 subset alongside, so one column stays directly comparable to the paper.

3. Confounds, stated before running

C1 — different model. Table 3 was measured on a single-task SFT model; we use the released multi-task pi05-b1kpt50-cs32. Absolute values should not match, and it would be suspicious if they did. The testable claim is the ordering within each arm.

C2 — ceiling. Fig 4 puts this task at 1.00 for the released checkpoint. H2 predicts an increase, which cannot be measured against a ceiling. If the baseline comes in at 20/20, the H2 arm can only show non-regression. H1 predicts a collapse, for which a ceiling baseline is ideal.

C3 — checkpoint identity is ambiguous. The README calls the released checkpoints both "base models ideal for fine-tuning" (the 0.192 pre-training stage) and "our latest models with Q Score of 0.345." Those cannot both be true. The baseline result discriminates: a 0.192-era model would not be at 1.00 on this task.

4. What is not reproducible

Table 3 #2 varies the trained chunk size {8, 16, 32, 50}. The released checkpoints are cs32 only, so reproducing it needs four separate trainings. We substitute max_len — how much of the predicted 32-chunk is executed before re-planning — and report configs E and F as a variant of H3, not a reproduction of it.

Table 3 #3 (input modality) needs checkpoints trained with depth/point-cloud inputs. Not released. Skipped.

5. Statistical treatment

All results reported as success rate with Wilson 95% confidence intervals, not bare point estimates. This matters more than it might appear:

Testing Fig 4's 1.00 claim
  10/10  ->  95% CI [0.72, 1.00]     rules out a true rate below 72%
  20/20  ->  95% CI [0.84, 1.00]     rules out a true rate below 84%

Table 3's headline resolution claim, 0.30 vs 0.60
  n=10   ->  [0.11, 0.60] vs [0.31, 0.83]     OVERLAP
  n=20   ->  [0.15, 0.52] vs [0.39, 0.78]     STILL OVERLAP

The paper's most-quoted ablation is not statistically resolvable at its own sample size, or at twice it. The same applies to Table 4's null results: "skill weighting yields no improvement" is indistinguishable from "we could not have detected one." Several reported effects are point estimates from ten trials, presented without intervals. This is a finding in its own right and does not depend on our runs completing.

6. Pre-registered predictions

Committed before running.

  1. Temporal Ensemble and Receding Temporal collapse to ≤ 0.10 while the baseline stays high.
  2. Native resolution beats 224×224, or ceilings alongside it.
  3. max_len=32 ≥ max_len=16 > max_len=8.

I expect H2 to hold most robustly and H1 to weaken. H2 has independent support: the RFT dataset's native resolution is exactly 720 (head) / 480 (wrist) — precisely Table 3's "high resolution" row. So the effect is plausibly "stop downsampling," which should transfer across checkpoints. H1's mechanism is entangled with how a single-task model's action distribution behaves, which is exactly what multi-task training changes.

7. Establishing the environment — three hypotheses, two eliminated

Getting a simulator to launch at all took most of the effort, and the diagnosis is part of the method rather than an aside.

og.launch() segfaulted on both available GPUs. The chain of elimination:

Hypothesis Test Outcome
PhysX GPU kernels missing for sm_120 (the forum explanation) gm.USE_GPU_DYNAMICS and ENABLE_FLATCACHE are already False by default — that path never runs ruled out
torch has no sm_120 kernels Real: torch 2.6.0+cu124 supports only to sm_90. Installed 2.7.0+cu128 — sm_120 present, CUDA matmul OK not sufficient, still segfaults
numpy ABI mismatch OmniGibson requires numpy<2.0.0; both machines had 2.2.6. Pinned to 1.26.4 fixed the 3090

With numpy pinned on both, and each machine running a torch build that supports its own architecture:

RTX 3090  sm_86    numpy 1.26.4  torch 2.6.0+cu124 (sm_86 ok)    og.launch() -> rc=0
RTX 5090  sm_120   numpy 1.26.4  torch 2.7.0+cu128 (sm_120 ok)   og.launch() -> SIGSEGV

One variable, two confounds eliminated first. The methodological lesson: a crash reproducing on two machines is evidence of a shared cause, not of the difference between them. An earlier version of this write-up attributed the segfault to GPU architecture before ruling out the environment, and was wrong.

Reportable defect in the reproduction path

setup.sh installs numpy 1.26.4 as OmniGibson requires, then the JoyLo dependency chain (mediapipe, mujoco, dm_control) silently re-upgrades numpy to 2.2.6, breaking the ABI for every pybind11 extension built against 1.x. Anyone running ./setup.sh --joylo --eval on a clean machine gets a simulator that segfaults with no usable error message. On the 3090 it surfaces first as TypeError: Unable to write from unknown dtype, kind=f, size=0.

Workaround: pip install numpy==1.26.4 after setup.sh completes.

Two further traps

  • setup.sh downloads the 2026 challenge task instances, but eval_custom.py reads 2025-challenge-task-instances/metadata/test_instances.csv. Nothing fetches it. Setup completes, then evaluation fails on a missing file. Fetch 2025-challenge-task-instances.zip from behavior-1k/zipped-datasets manually.
  • omnigibson.learning — the module openpi-comet overlays its eval code into — exists only in v3.7.x and was removed by 3.9. Cloning main produces a tree the competition code cannot use.

8. Execution

policy server   serve_b1k.py  ->  0.0.0.0:8000   XLA_PYTHON_CLIENT_MEM_FRACTION=0.25
2 sim shards    eval_custom.py policy=websocket, parallel_evaluator_start/end_idx
                staggered 45 s apart, separate OMNIGIBSON_APPDATA_PATH per shard

Both halves share the 24 GB card: policy ~6 GB, two Isaac shards ~7 GB each. Shard startups are staggered so they do not collide compiling the shader cache — each needs its own appdata path, which the upstream Slurm example achieves by keying the cache directory on GPU UUID.

The sweep is resumable: a config whose metrics directory already holds N_INST results is skipped, so an interrupted run continues rather than restarting.

Scoring: e3_score.py reports per-config success rate, Wilson 95% CI, the first-10 subset, and a consistent/inconsistent verdict against each value the paper printed.

9. Results

9.1 First attempt — invalidated by its own control

The first sweep ran the baseline at 224×224 and returned 0/20, with every instance terminating at exactly 4300 simulator steps and q_score.final = 0.000.

Config Paper n Success mean Q 95% CI
A_baseline_rh32_224 1.00 20 0.00 0.000 [0.00, 0.16]
B_temporal_ensemble 0.00 14 0.00 0.000 [0.00, 0.22]

Taken at face value this reads as "Fig 4's 100% claim does not reproduce." It is not a result. Config B is the tell: it agrees with the paper's 0.00 — and that agreement is worthless, because a harness incapable of producing any success returns 0.00 for every configuration, matching every prediction of zero it is tested against.

9.2 The positive control

Running the same policy on training instances it had already seen:

POSCONTROL (train, 224)   n=6   nonzero=0   meanQ=0.000
  -> ZERO_ON_TRAIN_TOO_harness_suspect

Zero on data the model was fitted to. That is not a policy failing to generalise; it is a broken apparatus. Every number in 9.1 was discarded.

This control was not in the original design, and should have been. Any experiment whose predicted outcome is zero cannot distinguish a confirmed hypothesis from a dead instrument without one.

9.3 Root cause — a misconfiguration of mine

Hypotheses tested and eliminated, in order: norm stats (load correctly from the checkpoint's own assets/); serving config (pi05_b1k-base matches pt50's training config on action_horizon=32, fine_grained_level=0, prompt_from_task=True); action_horizon=5 in the server log (the temporal-ensemble parameter, unused in receding-horizon mode); policy connectivity (websocket connected, robot moving); "No observations were recorded" (benign — the video-recording branch); action dimensionality (dim=32 is openpi's padded model space, not a mismatch).

The cause was image resolution:

224    on train instances:  n=6  nonzero=0  meanQ=0.000
NATIVE on train instances:  n=4  nonzero=1  meanQ=0.250

Upstream's base_config.yaml defaults env_wrapper to RGBWrapper (native 720/480) and the README states "We recommend to use the RGBWrapper for evaluation." I overrode that to RGBLowResWrapper (224) so the baseline would match Table 3's 224 row. That reasoning was wrong: Table 3's 224 numbers come from a single-task SFT model trained at 224. The released multi-task checkpoint requires native-resolution observations; at 224 it does not merely degrade, it fails completely.

9.4 H2 is not reproducible with the released artifacts

This kills the resolution arm outright. The 224 condition cannot be measured on this checkpoint, because 224 disables it rather than degrading it. Reproducing Table 3 #4 would require the per-resolution single-task models, which were not released.

So the paper's most-quoted ablation — native resolution doubles success, 0.30 → 0.60 — is unverifiable for two independent reasons:

  1. The artifacts needed to measure the 224 condition do not exist publicly.
  2. Even if they did, the CIs at n=10 (theirs) and n=20 (ours) overlap, so the comparison is not statistically resolvable at these sample sizes.

9.6 What this episode is worth reporting

The most transferable outcome of this reproduction is not a success rate. It is that a plausible-looking table of numbers — including one row that agreed with the paper — was produced by an apparatus that could not have produced any other answer, and only a positive control revealed it. The reproduction attempt was one control away from publishing a false negative about someone else's work.
