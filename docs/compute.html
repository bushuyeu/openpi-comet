Compute assessment — reproducing Openpi Comet (2512.10071v3)

Written before execution. Purpose: decide where to run, and what is actually reproducible at that scale, before spending allocation.

Paper: Team Comet, 2nd place, 2025 BEHAVIOR Challenge. π0.5 backbone, Q-score 0.2514 (test) / 0.345 (post-challenge validation). Fork: bushuyeu/openpi-comet (upstream mli0603/openpi-comet).

1. The decisive constraint: RT Cores

The paper states it plainly in §4.3, as its reason for choosing RFT over online RL:

"online RL requires a heterogeneous compute setup: GPUs with RT Cores are needed for simulation, while GPUs with Tensor Cores are needed for model training and rollouts."

BEHAVIOR-1K runs on OmniGibson, which runs on Isaac Sim. NVIDIA's Isaac Sim requirements list RTX-class GPUs only, and explicitly name A100 and H100 as unsupported because they have no RT Cores. Volta (V100) is further below that line.

This single fact reorders the whole fleet. Raw FLOPs and VRAM are close to irrelevant here — the simulator is the bottleneck and the gate.

Architecture Example RT Cores Runs OmniGibson?
Volta (sm70) V100 No No
Ampere GA100 A100 No No
Hopper H100 / H200 No No
Ampere GA102 A40, A10, RTX 3090 Yes Yes
Ada L40S, RTX 4090 Yes Yes
Blackwell RTX 5090 Yes Yes (needs Isaac Sim 5.x)

Note this cuts the opposite way from normal ML work. The paper trained on H200s — but you cannot evaluate on an H200, and evaluation is the only part of this paper reproducible at our scale.

Jetstream2 pi05-rlt A100 vGPU slice No 10–40 GB Ruled out. No RT Cores, and vGPU partitioning on top. 2000 SU ≈ 62–125 hr anyway.

Why Delta wins

  • A40 has RT Cores and 48 GB — comfortably above the repo's stated ceilings (inference > 8 GB, LoRA > 22.5 GB, full FT > 70 GB).
  • 100 four-way A40 nodes. The eval script takes parallel_evaluator_start_idx / end_idx, so the 10 instances per task shard 4-way across a node with no code changes. This matters more than anything else — see the runtime budget below.
  • 48 h walltime on production partitions; Apptainer available for the Isaac Sim container.
  • Largest allocation of the fleet.

Why Jetstream2 are out

Both are genuinely good boxes that are simply the wrong shape for this paper. Neither can render a frame of OmniGibson. Worth stating explicitly so we don't lose a day discovering it by running into a Vulkan error.

The one thing they're still good for

serve_b1k.py binds a websocket on 0.0.0.0:8000, and the sim connects with policy=websocket. Policy inference and simulation are therefore separable across machines, and inference needs no RT Cores. If A40 VRAM ever gets contended we can put the policy server on the DGX or Jetstream2 and keep only the simulator on Delta — the same heterogeneous split the paper describes. Cross-site latency and firewalling make this a fallback, not the plan.

3. What is actually reproducible

Ordered by cost. The honest headline: full reproduction is out of reach; the released checkpoints make the interesting claims testable anyway.

Claim Paper's cost Ours Feasible?
Pre-training (pt50) 50k steps, ~40× H200 — No. Config is literally named ..._gpu40.
RFT post-training 3 rounds × ~8500 rollouts ~3500+ GPU-hr No.
Per-task eval of released ckpt — ~30–60 GPU-hr Yes
pt12 vs pt50 comparison — ~30–60 GPU-hr Yes
Table 3 inference ablations — ~10–20 GPU-hr Yes — cheapest and sharpest
RFT dataset characterisation — 0 Yes, free

Proposed experiments

E3 — Table 3 inference-time ablations (run this first). The control-mode and resolution rows of Table 3 are pure inference flags, already wired:

scripts/serve_b1k.py:67  control_mode = "receeding_horizon" | "temporal_ensemble" | "receeding_temporal"
scripts/serve_b1k.py:70  max_len = 32

and resolution is one env flag — RGBWrapper swaps 224×224 for the native HEAD_RESOLUTION/WRIST_RESOLUTION.

No training. One short task (turning_on_radio, which Fig 4 shows at 100%). Falsifiable prediction from Table 3: temporal-ensemble and receding-temporal collapse to ~0, receding horizon does not, and full resolution roughly doubles success (0.30 → 0.60).

Caveat to state up front: Table 3 was measured on a single-task SFT model, not the released pt50 checkpoint. Absolute numbers should not match. The reproducible claim is the ordering, not the values.

E1 — Per-task eval of pi05-b1kpt50-cs32 against Fig 4's per-task accuracies and the 0.345 aggregate. There is a real ambiguity here worth resolving empirically: the README's Model Zoo calls these "base ... checkpoints ... ideal for fine-tuning" (suggesting the 0.192 pre-training stage), while the Updates line says they are the "Q Score of 0.345" models. Those cannot both be true. Measuring settles it.

E2 — pt12 vs pt50 on shared tasks. Not Fig 3 exactly (which sweeps pt1/7/10/50), but it tests the same claim — broader pre-training coverage unlocks more tasks — using only released artifacts.

E4 — Characterise delinqu/comet-1.5k (the released RFT dataset) against the paper's description: 8500 rollouts/round → 1469 kept after "de-duplication and task balancing". The paper credits refined task balancing for 0.224 → 0.345. Zero compute, and it's the only handle we have on the post-training claim.

Runtime budget

The paper warns evaluating one task takes "one hour to nearly a full day." Sharding 10 instances 4-way across an A40 node is what keeps this tractable.

Rough total: 150–250 A40 GPU-hours ≈ 40–60 node-hours on gpuA40x4. Well inside a normal ACCESS allocation, but I have not yet confirmed the balance.

Storage: checkpoints are Orbax (directory-per-parameter), ~14 GB each. The OmniGibson asset bundle is the large item — to be verified on scratch, not $HOME. The 10,000-episode challenge demo set (119 M frames, 90,000 videos) is not needed — evaluation uses only the checkpoint and its bundled assets/.../norm_stats.json.

4. Known risks

  1. Isaac Sim on HPC. The hard part of this whole exercise, and the most likely place to lose a day. Needs headless EGL/Vulkan in an Apptainer container, and a driver on the A40 nodes new enough for the pinned Isaac Sim. Verify before committing allocation.
  2. Delta MFA. Duo push on every fresh session, keys disabled. Blocks unattended automation; the ControlMaster socket must stay warm.
  3. b3iq is Windows. OmniGibson under WSL2 is not a supported path. The 5090 is also Blackwell (sm_120), needing recent Isaac Sim and JAX CUDA builds. Treat as a bonus target.
  4. KOA driver 590. Already recorded as hanging pi05. Even if KOA has RT-capable nodes, this needs clearing first.

6. Addendum — which clusters are worth signing up for

Re-run of the question against the wider national ecosystem, using the same RT-Cores filter. The filter is brutal: most NSF GPU capacity is A100/H100/V100/GH200, none of which can render a frame of OmniGibson. Requesting more of it would buy nothing here.

Do sign up

1. NRP Nautilus — highest value, sign up first. National Research Platform, free for research, Kubernetes rather than Slurm. It is the single richest pool of RT-capable GPUs in US academic infrastructure, and it exposes them as first-class schedulable resources:

GPU Request label RT? VRAM
NVIDIA A40 nvidia.com/a40 Yes 48 GB
RTX A6000 nvidia.com/rtxa6000 Yes 48 GB
Quadro RTX 8000 nvidia.com/rtx8000 Yes 48 GB
RTX PRO 6000 Blackwell nvidia.com/rtx6000bw Yes 96 GB
(general pool) RTX 4090 / 3090 / A5000 / L40 / 2080Ti Yes varies

Plus A100/H100/H200/GH200, which are useless for the simulator but fine for the policy server. ~1,000 GPUs, 9 PB storage, no allocation proposal needed. For an Isaac Sim workload this is arguably a better fit than Delta — no Duo, no queue, and you can pin an exact GPU model with a nvidia.com/gpu.product node affinity. Trade-offs: pods are preemptible, storage needs an explicit PVC, and you supply the container.

2. ACCESS Delta — keep, it's your only RT-capable ACCESS resource. Checked the ACCESS catalog: Delta's A40 nodes are the only clearly RT-capable GPUs in the entire ACCESS inventory. So Delta isn't just the best ACCESS option, it's effectively the only one. Worth requesting a larger allocation on rather than diversifying.

Don't bother requesting (for this paper)

None of these can run OmniGibson. Requesting them would waste the application:

They remain good for the policy server half of the split — but you already have surplus capacity there (DGX, Jetstream2). Tensor-core compute is not your bottleneck; RT-core compute is.

Revised recommendation

Run E3 on whichever comes up first:

  1. NRP Nautilus with nvidia.com/rtxa6000 or nvidia.com/a40 — likely fastest to first result, since signup is quick and there's no queue or MFA.
  2. Delta gpuA40x4 — better for the long batch sweep once it's set up (48 h walltime, 4-way sharding, non-preemptible).

These are complementary, not competing: prototype the container on Nautilus, then scale the sweep on Delta. Both use the same A40-class target, so the container transfers.

If you want a paid fallback with zero setup friction, an L40S or RTX 6000 Ada instance on Lambda / RunPod costs roughly a dollar an hour and would cover the whole E3 sweep for well under $50 — worth keeping in reserve if the Isaac Sim container fights back.
